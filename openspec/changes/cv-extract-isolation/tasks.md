## 2. Mecanismo de aislamiento (design D1, D2, D5, D6, D7)

- [ ] 2.1 [backend] `apps/worker/src/modules/cv/infrastructure/isolation/extraction-limits.ts` con las constantes de D5 (`CV_MAX_PDF_PAGES = 50`, `CV_MAX_RAW_TEXT_CHARS = 1_000_000`, `CV_DOCX_MAX_INFLATED_BYTES = 64 MiB`, `CV_DOCX_MAX_ENTRIES = 2_000`, `CV_THREAD_RESOURCE_LIMITS`, `CV_MEMORY_CEILING_BYTES = 512 MiB`, `CV_MEMORY_SAMPLE_MS = 100`, `CV_THREAD_BOOT_TIMEOUT_MS = 5_000`, `CV_ISOLATION_GRACE_MS = 2_000`) y `thread-protocol.ts` con los mensajes `ready | boot_error{code} | text{text, pagesCapped, rawCapped} | failed{cause}` y su validación (zod). Verificar con `extraction-limits.spec.ts`: «pins the isolation limits» (falla si cambia un valor) y con `thread-protocol.spec.ts`: «rejects a message outside the protocol» y «boot_error carries a code and no message».
- [ ] 2.2 [backend] `isolated-extraction.runner.ts`: crea el `Worker` con `env: {}`, `argv: []`, `execArgv: []`, `stdout: true`, `stderr: true` (drenados y descartados), `resourceLimits` y `workerData: { format }`; espera `ready` con `CV_THREAD_BOOT_TIMEOUT_MS`; transfiere los bytes copiados a un `ArrayBuffer` propio; un solo plazo desde la creación; `terminate()` en **todas** las salidas (`finally`). Ruta del script inyectable. Verificar con `isolated-extraction.runner.spec.ts` (scripts de hilo escritos por el test en `os.tmpdir()`): «returns the text a well-behaved thread posts», «terminates a thread that never yields when the deadline passes» (bucle `for(;;){}`, plazo 500 ms, resuelve en < 1,5 s), «always terminates the thread, also on success» (el evento `exit` llega). Falsación: quitar el `terminate()` del plazo y comprobar que «terminates a thread that never yields…» falla por tiempo.
- [ ] 2.3 [backend] Clasificación de D6 en el runner: `ERR_WORKER_OUT_OF_MEMORY` → `heap_limit`; salida ≠ 0 tras `ready` → `thread_exit`; plazo → `timeout`; `failed{cause}` del hilo → esa causa; `ENOENT`/`ERR_MODULE_NOT_FOUND` al crear, `boot_error`, sin `ready` en 5 s o mensaje fuera de protocolo → `CvExtractionMachineryError` (lanza). Verificar en el mismo spec: «heap exhaustion is unreadable and the process survives» (array creciente; tras el desenlace, otra extracción del mismo runner devuelve texto), «a thread exiting with code 3 after ready is unreadable», «a missing thread script throws a machinery error», «a thread that never says ready throws a machinery error», «boot_error throws a machinery error with the code only». Falsación: clasificar `boot_error` como `unreadable_file` y comprobar que el test correspondiente falla.
- [ ] 2.4 [backend] Vigía de memoria (D5): muestreo de `process.memoryUsage.rss()` cada `CV_MEMORY_SAMPLE_MS` desde la creación del hilo; supera la base + techo → `terminate()` de las lecturas en curso → `memory_ceiling`; el intervalo se limpia siempre. Techo inyectable para el test. Verificar: «the memory watchdog terminates a thread that allocates off-heap buffers» (hilo con `Buffer.alloc(32 MiB)` en bucle y techo de 256 MiB inyectado; desenlace `memory_ceiling`, proceso vivo), «the watchdog interval is cleared after every extraction» (sin temporizadores pendientes: `vi.getTimerCount()` o contador del runner). Falsación: subir el techo inyectado a 64 GiB y comprobar que el primer test acaba por plazo, no por vigía.
- [ ] 2.5 [backend] Hilo sin secretos y sin voz (D7). Verificar en el spec del runner: «the thread sees an empty environment» (con `process.env.S3_SECRET_KEY` puesto en el test, el hilo publica `Object.keys(process.env).length === 0`), «nothing the thread writes reaches the logs» (hilo que escribe `CANARY-THREAD-OUTPUT` en `stdout` y `stderr`; registro de pino capturado sin esa cadena y salida del proceso de test sin ella). Falsación: quitar `env: {}` y comprobar que el primer test falla.
