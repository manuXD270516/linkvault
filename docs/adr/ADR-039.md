# ADR-039 — Funnel personal de postulaciones (analytics on-read)

**Estado:** Accepted · **Fecha:** 2026-09-23 · **Change:** `application-analytics`

**Origen:** design.md F3 `analytics` + reflect critic/business. Relacionados: ADR-024 (estados /
`CLOSED_STATUSES`), ADR-035 (ApplicationStale / umbral 10 días).

## Contexto

El kanban guarda estados y timeline, pero no hay resumen del embudo. Hace falta un insight de
**lectura** sin dual-write de métricas ni discovery.

## Decisión

1. **On-read:** `GET /api/applications/analytics` agrega sobre `applications` del dueño. Sin
   colección de métricas.
2. **Buckets:** reutilizar ADR-024 / `CLOSED_STATUSES` (`rejected|withdrawn|expired`).
   - `closedCount` = statuses en `CLOSED_STATUSES`
   - `acceptedCount` = `accepted` (no es “cerrado”)
   - `openCount` = total − closed − accepted
3. **Stale (insights):** umbral **10 días** (= ApplicationStale / `APPLICATION_STALE_AFTER_DAYS`).
   Elegibilidad: `!isClosedStatus(status) && status !== 'accepted'`. Cap **20**, orden más
   antiguas primero. Shape dueño: `{ applicationId, linkId, status, statusChangedAt }`.
4. **Diferencia vs email B4:** el detector de notificaciones stale puede seguir incluyendo
   `accepted` (solo excluye `CLOSED_STATUSES`). Insights **excluyen** `accepted` a propósito;
   no se cambia el detector en este change.
5. **Fuera:** funnel de grupo; dwell / tiempo medio en etapa; dual-write.
6. **Plan:** fila 25 en `docs/design-v0.2.md` §6.

## Alternativas descartadas

- Materializar métricas en colección (YAGNI).
- Incluir grupo en el mismo change (ACL/vanity; change propio si hay demanda).
- Dwell desde `application_events` en MVP (ruido con poco historial).

## Consecuencias

- API + SPA insights personal.
- Shared schemas del response analytics.
