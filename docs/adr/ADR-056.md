# ADR-056 — Filtro de salida para las descargas iniciadas por datos de usuario y push solo a servicios push

**Estado:** Propuesto · **Fecha:** 2026-10-28 · **Origen:** relevamientos independientes de critic y del arquitecto
(2026-10-28) y design del change `enrichment-egress-guard`.
**Exceptúa (Q1 = (a), decidida por el owner el 2026-10-29):** la precedencia de la fila 35 de ADR-048 §Consecuencias, con el alcance de ADR-051
§1 y su §Enmiendas, punto 3 (ver §1).
**Toca:** ADR-003 y ADR-022 (la descarga con cortesía: cambia el transporte, no la política), ADR-035 (web push),
ADR-037 (la frescura reutiliza la descarga) y ADR-051 §5 (registro abierto en staging).

## Contexto

LinkVault abre conexiones hacia donde dicen las URLs que escriben las personas: la página de una oferta, su
`robots.txt` y sus redirecciones (enriquecimiento y frescura), y el endpoint push que declara el navegador. Ninguna de
esas salidas comprueba hoy a qué dirección de red llega: la API acepta cualquier host, el descargador de la página solo
mira el esquema, el del `robots.txt` sigue redirecciones sin contar ni mirar y lee el cuerpo entero, y el alta push
guarda cualquier URL. El worker comparte red con servicios internos que confían en quien ya está dentro. Con el
registro abierto de staging (ADR-051 §5), cualquier persona registrada podría hacer que el servidor pida recursos de
direcciones internas o de metadatos del proveedor de nube.

### 2. Un filtro de salida, en la resolución de nombres del cliente HTTP

Toda conexión hacia una URL de usuario —página, `robots.txt` y cada redirección de ambos— pasa por un filtro que
resuelve el nombre y rechaza si **cualquiera** de las direcciones resueltas no es pública (loopback, privadas, enlace
local, `100.64.0.0/10`, `0.0.0.0/8`, multidifusión, difusión, reservadas, documentación; en IPv6, todo lo que esté
fuera de `2000::/3` y, dentro, ULA, enlace local, mapeadas, compatibles con IPv4, `2001::/23` y la documentación
`2001:db8::/32` y `3fff::/20`; las de traducción se juzgan por su IPv4 interna), rechaza sin resolver los nombres sin
punto y `localhost`, y solo admite el puerto por defecto u `80`/`443`, decidido con la clase del host antes de
resolver. La política es una interfaz (`EgressPolicy`: host, dirección, puerto) cuya única implementación de producción
es la pública. El filtro vive en un **conector propio** del `Agent` de `undici`, que clasifica el host y el
puerto de cada conexión (nombre o literal, en cualquier salto) y resuelve los nombres con su propio `lookup`, así que la
conexión se abre contra las direcciones comprobadas y no hay segunda resolución que un cambio de DNS pueda aprovechar.
Las redirecciones las sigue el llamador, a mano; sin HTTP/2 compartido entre orígenes y sin proxy del entorno. La
verificación TLS no se desactiva nunca; los tests suman su autoridad a las raíces del sistema
(`ca: [...tls.rootCertificates, ca]`), porque pasar `ca` sola las sustituiría. La
clasificación vive una sola vez en `libs/shared` (subruta `@linkvault/shared/net`, fuera del SPA) y la usa también la
API, con la política pública y sin inyección, para rechazar, sin DNS, el host que se ve en la URL al guardar; el puerto no se juzga al guardar, para que la persona
no pierda el link.

Un rechazo deja el link en `failed` con el motivo nuevo `unsafe_destination`, no reintentable, que no cierra vacantes
por frescura y que se registra sin URL, host ni dirección. En el `robots.txt`, un rechazo, más de cinco saltos, un
salto a otro host que no sea a `/robots.txt` sin query o un cuerpo sobre el tope significan «no disponible».

*Descartado:* validar solo en la API (no ve lo que resuelve el DNS cuando conecta el worker); resolver aparte y
conectar a la IP reescribiendo la URL (rompe TLS); elegir entre las direcciones resueltas la pública.

### 3. Push solo a los servicios push conocidos

El endpoint push se valida contra una lista de servicios push (FCM, Mozilla, Apple, Windows) en el alta y otra vez
antes de enviar, con un criterio de URL que los dos analizadores implicados no puedan leer de forma distinta (texto ya
canónico, juego de caracteres del host restringido y, antes de enviar, el mismo host en ambos); los guardados antes
que no cumplan se borran sin conectar, registrando el host y nunca el endpoint completo. La lista es código, no
configuración. Si el alta se rechaza, el SPA cancela la suscripción local del navegador y lo trata como navegador sin
soporte push, con el texto que ya existe.

*Descartado:* aplicar el filtro de §2 al push (seguiría enviando peticiones firmadas a cualquier host público) y una
lista configurable por entorno.

### 4. Ninguna configuración relaja el filtro

No hay variable de entorno que abra destinos locales, en ningún entorno. Los tests que necesitan un servidor local
inyectan en código una política de test completa. Si un change futuro necesita enriquecer contra un servidor local, la
variable entra con ese change, y nunca podrá abrir `100.64.0.0/10`, `fc00::/7`, enlace local ni las demás categorías
que no son loopback, RFC 1918, `localhost` o nombres sin punto.

### 5. Lo que este filtro no cubre

- Una etapa headless futura resuelve y conecta por su cuenta: cuando tenga adaptador, tendrá que salir por este mismo
  filtro.
- Un proxy de salida haría que el filtro comprobase la dirección del proxy; usarlo sería una decisión con su propio
  filtro.
- Las salidas que no parten de datos de usuario (IA, correo, `job-discovery`, almacén) no pasan por él.

### 6. Recomendación para 35b (`staging-host`), fuera de este change

Defensa en profundidad del lado del despliegue, porque el filtro protege solo las conexiones iniciadas por URLs de
usuario:

- red propia para el worker que solo alcance los servicios que necesita y la salida a Internet;
- autenticación o filtro por dirección de origen en las interfaces del almacén de objetos que hoy no la piden;
- contraseñas en Redis y Mongo aunque estén en una red privada;
- métricas de la API no alcanzables desde el worker;
- bloqueo a nivel de host de la dirección de metadatos del proveedor para los contenedores que no la necesitan.

Trasladarla a los artefactos de `staging-host` es la Q3 del change. Respuesta del owner (Q3), 2026-10-29: la
recomendada, un PR solo de spec tras la aprobación de este change, con el texto de esta sección y sin cambiar el orden
de tareas de 35b (pendiente de abrir; este change no edita `openspec/changes/staging-host/`).

## Consecuencias

- Una página pública cuyo DNS devuelva alguna dirección interna deja de poder leerse; el motivo lo dice.
- `unsafe_destination` entra en la lista cerrada de motivos. Revertir el change **reabre el defecto**: revertir exige
  que el despliegue tenga antes la defensa de §6. Si hay que actuar antes de tenerla, la contingencia es pausar la
  cola `enrich-link`, que es la única (la frescura la reutiliza), con un script de `Queue.pause()`/`resume()`, no
  revertir; el respaldo es parar el worker, aceptando que se cortan el correo y el push. La corrección posterior es una
  fusión correctiva (clase 1 antes de la 10.7; después, con las reglas de las clases 2 y 3). Si se revierte, esos motivos pasan a `blocked` (no reintentable,
  no cierra por frescura, no dispara el rescate por historial) con el orden parar el worker → actualizar → desplegar el
  anterior → repetir la actualización (Migration Plan del design).
- `undici` e `ipaddr.js` pasan a `dependencies` de la raíz; `selfsigned`, a `devDependencies`. El `package.json` que
  genera el build de la API y del worker se comprueba: lleva las de producción y no `selfsigned`.
- Un navegador con un servicio push fuera de la lista no podrá suscribirse hasta ampliarla; el correo no cambia.
- El SPA cambia lo mínimo: cancela la suscripción local ante un alta rechazada y muestra el texto existente de
  navegador sin soporte push; el motivo nuevo usa el texto genérico
  existente, pide a una persona y no ofrece reintentar.
